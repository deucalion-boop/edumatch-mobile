## Device acceptance procedure

Use test accounts in the school's staging environment and two physical development builds, with the server migrations applied and its push worker running.

1. Sign in as each role with CAPTCHA and email OTP. Relaunch to check SecureStore rehydration. Revoke that session through the existing web interface and verify the app returns to sign-in after the next authenticated request. Verify the forced-password workflow.
2. Verify Admin/Principal approvals and school metrics, Secretary records/export requests, and Head Teacher department academic/attendance scope. Confirm an account cannot access another role's routes or data through direct API requests.
3. As Teacher, approve subject enrollment and publish a lesson with a required PDF plan. As Student, move through lesson and assessment pages with at most five records each; open a lower record, scroll its reader, and use Back to confirm the previous list page and position remain. Check Android hardware Back, iOS safe areas, and the assessment keyboard. Open files and submit written/link/file responses. Review those submissions as Teacher, record points/feedback, and confirm server-generated Student grades. Exercise exam start/save/submit and server locks.
4. Open a Teacher QR session for today's school date. Scan as an approved Student; scan again and confirm a duplicate result. Rotate the code and confirm the old image is rejected. Confirm an unenrolled Student and another Teacher cannot use the session.
5. Review the Teacher roster, apply an Excused override, and finalize. Check Present/Late/Absent/Excused totals through mobile and existing web attendance views. Verify further scans and edits are rejected. Verify manual attendance cannot overwrite an open QR session and finalized records cannot change.
6. Deny camera access and confirm permission recovery. Background the scanner and verify the preview stops. Disconnect networking during a scan, reconnect, and retry without duplicate official attendance. Confirm failed mutations show an actionable error.
7. Enable notifications on Android and iOS, publish a school announcement, and confirm device delivery and authenticated inbox navigation. Revoke or sign out the bound account; ensure new queued messages are cancelled. Check invalid tokens and delivery receipts in the worker.
8. Produce signed EAS development and production builds for both platforms. Check installation, icons/splash, permissions, API HTTPS configuration, upload/download behavior, accessibility and keyboard layouts on actual screen sizes before store submission.

For the updated login, also check the password visibility toggle, keyboard scrolling on a small phone, and the centered wide-screen sign-in form. Relaunch after an unchecked "Remember me" login and confirm that sign-in is required again. Password recovery should show a generic confirmation and deliver the existing web reset link for a registered staging account. OTP timing should follow the server's absolute expiry/resend timestamps after backgrounding the app; every sign-in and OTP verification opens a fresh CAPTCHA check.

The upgrade follows [Expo's SDK upgrade guide](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/). TypeScript 6 requires an explicit Node types opt-in for the existing `node:test` tests, so `@types/node` is declared directly and `compilerOptions.types` includes `node`; see [TypeScript 6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html). Use `npm start -- --clear` (or `npm run start:go -- --clear`) for Expo Go SDK 57. `npm run start:dev` targets an EAS development client, which must be rebuilt after this SDK upgrade.

The Expo Go launch follow-up on October 10 found that the running server's default link targeted the custom development client, despite its manifest reporting SDK 57. `npm start` now explicitly targets Expo Go; `start:dev` preserves the development-client command. Native notification APIs are loaded only outside Expo Go and web, preventing Android's unsupported push listener from throwing during imports or after sign-in. Strict TypeScript and all 17 app tests passed, including three runtime tests that reject notification imports in Expo Go/web and allow them in development/standalone builds. An isolated server displayed `Using Expo Go`, returned an `exp://` launch URL with SDK 57.0.0, and served the Android development bundle with HTTP 200. Physical phone launch and LAN reachability from the phone remain unverified.

The lockfile uses the Expo SDK 57 compatible native dependency set. `npm audit` currently reports transitive advisories in the Expo/Metro/React Native toolchain. Its suggested forced downgrades conflict with the chosen SDK; they were not applied. Recheck patched compatible dependency versions before publishing. No zero-vulnerability or production-readiness claim is made.
